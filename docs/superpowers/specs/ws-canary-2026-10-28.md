# Websocket canary: is Railway or Cloudflare resetting long-lived sockets?

## Goal

Find which network hop resets uw-stream's UW websocket connections (50–260 drops a day), by holding identical long-lived websockets from the same Railway region to the same echo server with and without Cloudflare in the path. Temporary: delete after the comparison.

## What we know (2026-10-28 investigation)

- Every drop is `ConnectionClosedError: no close frame received or sent`: the TCP connection ended without a websocket close frame. Not our keepalive (that would read `sent 1011 … keepalive ping timeout`).
- On single-socket drops, UW kept sending after our socket died (Railway `NO_SOCKET` drops), and the socket-killing packet is a 54-byte bare TCP segment arriving ~2 ms after our ping. TCP to UW ends at Cloudflare's edge, ~2–3 ms away, so the reset comes from Railway's network or Cloudflare's edge.
- Drop rate: 7.9/h in the options session, 3.6/h futures-only hours, 1.5/h Globex closed. Connection lifetimes are random (0–745 min), so no fixed age limit.
- Memory: `project_uw_stream_disconnects_2026_10_28.md`.

## Design

One Python process, four connections, same region as uw-stream (`us-west2`), same client library and keepalive as uw-stream (`websockets==17.3`, `ping_interval=20`, `ping_timeout=20`):

| Connection      | URL                                             | Traffic                               |
| --------------- | ----------------------------------------------- | ------------------------------------- |
| `cf-quiet`      | `wss://ws.ifelse.io` (Cloudflare → Fly)         | pings only                            |
| `cf-chatty`     | `wss://ws.ifelse.io`                            | ~200-byte text every 1 s, echoed back |
| `direct-quiet`  | `wss://echo.websocket.org` (Fly, no Cloudflare) | pings only                            |
| `direct-chatty` | `wss://echo.websocket.org`                      | ~200-byte text every 1 s              |

Both hosts are the same Fly-hosted echo service (verified `server`/`via` headers 2026-10-28); the only difference is Cloudflare in front of `ws.ifelse.io`.

- Real `User-Agent`: `strike-calculator-ws-canary/1.0`.
- Reconnect 1 s after a connected session drops; back off 1 → 60 s across consecutive failed connects (reset on the next successful connect). A refusing host (`echo.websocket.org` returns HTTP 429 to a 4th socket from one IP) then logs about one line a minute, not one a second.
- One JSON stdout line per drop: `conn`, `url`, `exc_type`, `err`, `close_rcvd`, `close_sent`, `cause_type`, `cause`, `cause_errno`, `session_s`, `frames`, `since_last_frame_s`, `local_addr`, `remote_addr` — the same fields as uw-stream's disconnect diagnostics (`fix/uwstream-disconnect-diag`), so the two logs compare line for line.
- One heartbeat line every 10 min: per connection, up/down, drops since boot, frames since boot.
- No env vars, no secrets, no Sentry, no DB. Logs only (Railway keeps ~30 days).

## Reading the result

Compare drops per hour, per regime (options session / futures-only / closed), against uw-stream over the same hours:

| Canary result                                                                  | Points to                                                                    |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| Both `cf-*` and `direct-*` drop like uw-stream, with the same 2 ms reset shape | Railway's network                                                            |
| Only `cf-*` drops                                                              | Cloudflare's edge (raise with UW: their WS sits behind Cloudflare)           |
| Neither drops                                                                  | Something specific to UW's path or account (token use, UW origin, Google LB) |
| Chatty drops more than quiet                                                   | Volume-sensitive middlebox (matches uw-stream's activity correlation)        |

Minimum per run: one full options session plus one overnight (run 1 Serverless on, then run 2 Serverless off — see below).

**Serverless as a third factor (added 2026-10-28).** uw-stream runs with Railway Serverless ("app sleeping") on. It never sleeps (its pings are outbound traffic), but Railway documents that Serverless "de-prioritizes your workload". The canary tests it in sequence, not with a second service: `echo.websocket.org` refuses a 4th socket from one IP (HTTP 429), and two services in one region can share an egress IP, so a second copy would knock out a `direct-*` arm. Run 1: Serverless **on** (matching uw-stream) for at least one options session and one overnight. Run 2: Serverless **off** for the same span. Both use `us-west2`, IPv6 egress off and runtime V2, as uw-stream does. If drops fall in run 2, turn Serverless off on uw-stream.

**429s are not drops.** A sustained `InvalidStatus … HTTP 429` on a `direct-*` connection means another client on the same egress IP holds sockets to `echo.websocket.org`. Those are failed connects (`session_s` null) and don't count as drops; that arm's coverage is lost while they last, so discount it for that window.

## Phases

1. **Build** (this spec): `scripts/ws-canary/` — `canary.py`, `test_canary.py`, `requirements.txt` (`websockets==17.3`), `Dockerfile`, `railway.toml` (restart ALWAYS, watch pattern `/scripts/ws-canary/**`), `README.md`. `scripts/` is already in Vercel's `ignoreCommand`, so the canary never triggers a Vercel build.
2. **Deploy**: one Railway service, `ws-canary`, in project Theta-Options, region `us-west2`, root directory `/scripts/ws-canary`, Dockerfile builder, restart policy ALWAYS, watch path `/scripts/ws-canary/**`, Serverless on (run 1), IPv6 egress off, connected to this repo's `main`. Owner approved 2026-10-28. New Railway services can't use Config as Code (it is deprecated and stops being read on 2026-12-01), so these settings go on the service itself; `railway.toml` only records them. After run 1, switch Serverless off and redeploy for run 2.
3. **Read** after each run; write the verdict into this spec and the disconnects memory. Compare uw-stream's diagnostic drop lines (`cause_type`, `session_s`, `local_addr`) with the canary's over the same hours.
4. **Remove**: delete the Railway service (ask the owner first) and the directory.

## Open questions

- Echo-server rate limits or idle policies could add their own drops. Default: if one host drops on a fixed schedule, note it and discount that host.
- IPv6 vs IPv4: `ws.ifelse.io` resolves IPv6 first; Railway egress may be IPv4-only. Default: let the resolver choose and log `remote_addr`.
