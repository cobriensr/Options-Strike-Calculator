# Sentry noise fixes (2026-11-13)

## Goal

Make each Sentry email mean one real problem. Before the owner unmuted the cron monitors on 2026-11-13, a week of data showed:

- Most error volume came from a few reporters that send the same failure many times.
- Some check-ins were lost even though the job had run fine.

This plan removes the repeats and keeps every real failure visible.

### Phase 2: a transient Neon error in a cron is a warning, not a Sentry error

- **Cause.** `api/_lib/cron-instrumentation.ts` ~838 calls `Sentry.captureException(err)` on any thrown error, with no test for `TransientDbError`. Endpoints already treat transients as a warning plus a metric, with no exception capture (`transient-db-response.ts:71-82`; policy stated in `request-scope.ts:133-143`).
- **Fix.** Use the same policy in the cron wrapper:
  - log at warning level, count `cron.db_timeout` (one metric for every cron, attribute `job`; see "Decided" below), and skip `captureException` for `TransientDbError`;
  - the check-in still reports `error`, because the run failed.
- **Files.**

  - `api/__tests__/transient-db-error.test.ts`.
- **Deploy.** Vercel. Push outside market hours.

"Unmuted" means each of those monitors reads back `isMuted: false` through the Sentry monitors API. Until then, a cron's exception is its only email path, because many monitors are muted. This change removes that exception for a transient Neon error, so a muted monitor would leave the failed run with no email at all.
  - Met 2026-11-14 about 03:30 UTC. `fetch-vol-0dte` was deleted and the 46 other muted monitors were unmuted. A read-back showed 82 monitors, none muted at the monitor or environment level.

### Phase 3: uw-stream reports a reconnect storm once per incident, and files each exception once

- **Cause.**
  - `uw-stream` `connector.py` `_maybe_alert_storm` (~544-561) calls `capture_message` on every reconnect past the threshold, with no cooldown. That made 30 events on 11-12 17:32 to 18:05 UTC.
  - `sentry_setup.py` logs at ERROR (~155-158) and then calls `capture_exception` (~168). The SDK's default `LoggingIntegration` (event level ERROR, sentry-sdk 2.73.0) turns the log record into a second event.
- **Fix.**
  - **Storm cooldown.** At most one alert per 3600 s, process-wide (`_maybe_alert_storm` in `connector.py` reads `RECONNECT_HORIZON` from `state.py` each time it runs, with no constant of its own; the timestamp is `state.storm_alerted_at`, one float). A test patches the horizon to ten minutes and checks the window follows it.
    - Why 3600 s: it equals the horizon `reconnects_last_hour` counts over, one constant, `RECONNECT_HORIZON` in `state.py`, that both read. Once a burst crosses the threshold the count stays above it until the burst ages out of that hour (11-12: 17:32 to 18:05 UTC, about one reconnect a minute, peak 55). A window as long as the horizon means every reconnect behind an alert has aged out when the window ends, so the next alert needs a threshold's worth of new reconnects. A shorter window would alert again on reconnects the first alert had already counted.
    - Why process-wide: the count and the threshold (base times the shard count) are both process-wide, and drops arrive as all-shard clusters about 41% of the time. A timestamp per connector would send one alert per shard for one incident.
    - Cost: a second incident that starts inside the hour of an earlier alert is not announced. Each of its drops still logs one line and shows in `/metrics` `reconnects_last_hour`. A storm still going when the hour ends alerts again.
  - **One event per failure.** `LoggingIntegration(level=INFO, event_level=None)`, as `nightly/src/monitoring.py:68` already does. An error log line is a breadcrumb on the next event, never an event.
  - **Explicit captures added where the log line was the only Sentry path.** Each sits beside its `log.error` and carries tags that say what it is:
    - `RateLimitedLogger.error` (`logger_setup.py`) sends a `capture_message` at level `error` for its head-of-window line, so the throttle bounds events as it bounds lines. This covers `futures_front_month._fail` and `futures_trades._note_failure`. A warning sends nothing.
    - The front-month clamp in `futures_front_month.py` (kind `front_month_clamped`).
    - `futures_trades._note_unknown` (kind `front_month_unknown`), a completed minute skipped for want of a front-month contract. It sends once per product per window with the running total and the cause.
    - `main._shutdown`'s "handler drain raised", sent with `capture_exception` and tags `component=main`, `stage=drain` and the handler name.
  - **Library loggers (review finding, fix round 1).** `event_level=None` also dropped the ERROR records of libraries, which log a failure and send nothing else. `init_sentry` now attaches an `EventHandler(level=ERROR)` to the `websockets` and `asyncio` loggers, once (a second call attaches nothing) and only after `sentry_sdk.init` succeeds, so a service with no DSN attaches nothing. What it catches, in the installed websockets 17.4 and CPython 3.12:
    - `websockets/asyncio/connection.py` "keepalive ping failed" (the socket stays open with no pings) and "unexpected internal error";
    - `websockets/protocol.py` "parser failed";
    - asyncio's "Exception in callback" (built in `asyncio/events.py`, `Handle._run`) and "Task exception was never retrieved" (built in `asyncio/futures.py`, `Future.__del__`, as `f'{self.__class__.__name__} exception was never retrieved'`, so the class name supplies "Task" and a grep for the literal finds nothing; the C accelerator builds the same text). Both go through `call_exception_handler`, whose default handler in `asyncio/base_events.py` logs them at ERROR.
      WARNING records of these loggers stay breadcrumbs. The service's own logger is not touched, so its error lines still file nothing. One side effect handled: any handler on a logger ends the stdlib's last-resort stderr line for that logger. Neither logger has a handler of its own (websockets 17.4 adds no `NullHandler`) and nothing configures the root logger, so before this change both loggers' WARNING and ERROR records reached stderr, and so Railway's logs, through `logging.lastResort`. That is why `init_sentry` attaches `logging.lastResort` to each of them when no handler is in its chain, which keeps those lines. The choice is made once at init. Root logging configured before `init_sentry` (`basicConfig`, a root handler) is already handled: `hasHandlers()` is then true and the branch is skipped (a test pins it, with a real root handler and no patch on `hasHandlers`). Root logging configured after `init_sentry` is not: `lastResort` is already attached, and the branch must be dropped, or these loggers print every WARNING and ERROR line twice. It is also skipped when `logging.lastResort` is `None`.
  - **What reaches Sentry now:** the explicit captures, the two library handlers, `AioHttpIntegration` (an exception the health handlers don't catch) and `ExcepthookIntegration` (an uncaught exception). Both integrations are active under the current `init` kwargs (a test checks this on a client built with the default integrations on).
  - **Connect-time log lines (follow-up, 2026-11-14).** Railway drops a replica's log lines past 500 a second. It reported drops on 11-11 (17 lines), 11-13 (52) and 11-14 at 02:39 UTC (35, right after a deploy). A connect logged `sent join frame` (connector) and `channel ack received` (router) at info for each of about 250 channels inside one second, and anything else logged in that second, a real error included, could go with them.
    - Both lines are now debug. The service logger's level is INFO, so production does not emit them.
    - Each connector logs one line per shard instead, from `Connector._report_join`:
      - `shard joined` (info) with `shard`, `channels`, `acked` and `elapsed_s`, once every one of its channels is acked;
      - `shard join incomplete` (warning), with the same fields plus `unacked` (the name of every unacked channel), when some are still unacked `_RESUBSCRIBE_INITIAL_DELAY_S` (30 s) after the joins began. That is the wait the reconcile pass already gives the acks, so no timeout is added.
    - It reads the `state.channel(ch).subscribed` flags the router sets, the ones `_reconcile_once` reads: no second tracker. It runs as one task per connection, polling every `_JOIN_SUMMARY_POLL_S` (0.1 s), cancelled with the socket (a drop before it logs leaves no join line and no task), and it sends nothing. Subscription, sharding, retries and timeouts are unchanged.
    - A join UW never answers, one lost on the wire and one UW refuses with an error frame (`{"error": ...}`, which the router forwards to the handler like data) all leave the flag False, so all three show as `unacked`. The warning is one per shard, not one per channel, so a shard that fails whole cannot repeat the burst. Before this, a refused join was named only in the first 10 names of the reconcile warning ("re-sending joins for stuck channels") and in the watchdog alert; both stay.
    - Limit: the flag is per channel name, not per socket, so on a mirrored `option_trades` channel the twin socket's ack counts as this shard's.

### Phase 4: 429 reporting

- **UW.** `metrics.uwRateLimit` (`api/_lib/sentry.ts` ~159-167, called from `uw-fetch.ts:273`) sends one warning per 429 call, and the endpoint path is in the message, so each endpoint opens its own issue. Report once per run per endpoint, and only when the retries ran out.
- **GEXBot.**
  - `gexbot-client.ts` labels a 429 "quota", and `uw-fetch.ts:70` treats it as a daily quota.
  - **Basis (corrected 2026-11-14, after a verifier read the vendor's docs, spec 2.17.0, and 30 days of Sentry).** The first draft said the vendor contract quoted in `gexbot-client.ts:14-22` is a rate limit of one request per second per ticker per metric. That line is AGENTS.md's polling advice, not an enforced limit, and it does not support the change. What does:
    - The vendor documents a per-account short-window limit: a 429 with `Retry-After`, counted over a window such as a second or a minute, all keys together.
    - It also documents daily and monthly pool quotas per endpoint, lasting until midnight ET. The docs say nothing about whether a quota 429 carries `Retry-After` (the page says only that a short-window 429 does). These quotas exist, so a live-route 429 is not shown to be a short limit.
    - The only 429s in 30 days were 4 calls within about 120 ms on 2026-11-11, none after (the 11-06 to 11-13 week shows the same 4). One transient burst is enough for a bounded retry, not for a claim about which limit it was.
  - So: retry a live-route 429 a bounded number of times, count it, and put on the exhausted event the evidence for which kind it was (`Retry-After` present or not). The EOD route keeps treating a 429 as a quota and stops; that is unchanged.

- **Built (2026-11-14).**
  - **UW: count every 429, report only a 429 the retries gave up on.**
    - `uwFetch` now throws `UwHttpError` (`uw-fetch.ts`) for every non-2xx. The message is unchanged (`UW API <status>: <body>`), `name` stays `Error` and V8 leaves the constructor frame off the stack by itself, so Sentry groups it as the plain `Error` it replaces (the `beforeSend` test that other 4xx are not collapsed still holds). It carries `status`, `endpoint` and `retryAfter` (the raw header).
    - Every 429 calls `metrics.uwRateLimit(endpoint)`: a count of `uw.rate_limited`, attribute `endpoint`, and no Sentry event. Before, it also sent a warning per 429, with the path in the message.
    - `endpoint` is `uwEndpointTemplate(path)`, so it is bounded by the UW route list. The query string is dropped, an ISO date segment becomes `{date}`, and any segment that is not a lowercase word (`[a-z_-]+`: ticker, option symbol, futures contract, expiry, candle size) becomes `{id}`. `/stock/SPY/greek-flow?date=2026-11-13` is `/stock/{id}/greek-flow`. The old value was the raw path, so the existing `uw.rate_limited` series changes label values on deploy (query `sum(value,uw.rate_limited,counter,-)` grouped by `endpoint`).

Every endpoint groups into one issue; the endpoint is a tag, not text in the message. The caller still gets the thrown error and reports its own failure (a cron goes red; the cron wrapper also captures the thrown error as before).
    - **Run scope: none, by choice.** The spec's "once per run per endpoint" has no clean scope to hang on. `withCronInstrumentation` deliberately does not open an isolation scope (see its comment at the check-in call), so a `WeakMap` on the scope has nothing to key on, and any module-level set or map would outlive the request under Fluid Compute (R1). "Only when the retries ran out" plus one fingerprint is the bound: a run whose N calls all exhaust files N events into the one issue.
    - A call with no retry loop around it (`uwFetch` called bare) is counted, and `withRetry` never sees it, so nothing is filed by this path. By grep, `iv-term-structure.ts`, `analyze-context-fetchers.ts`, `max-pain.ts`, `spx-candles.ts`, `uw-spot.ts`, `uw-stock-candles.ts` and `vix-term-structure.ts` call it with no `withRetry` in the file (a caller may add one).
  - **GEXBot: a live-route 429 is retried with backoff and counted.**
    - `classifyRetryDelay` (`uw-fetch.ts`) no longer returns `null` for `GEXBot 429`. The wait before retry `n` (0-based) is `max(Retry-After, 1000 × (n + 1))` plus 0-250 ms of jitter: 1 s, then 2 s with no header. With the default 2 retries (3 attempts) a persistent 429 costs 3.5 s of waiting at most with no header (1 s + 2 s + jitter) and 6.5 s at most with a 3 s `Retry-After` (two waits of 3 s + jitter). Both are under the 10.5 s worst case that `GEXBOT_TIMEOUT_MS` documents, and a 429 answers fast, unlike a timeout.
    - `Retry-After` is parsed in `gexbotFetch` (delta-seconds, or an IMF-fixdate read against the clock) and kept on `GexbotHttpError.retryAfterMs`; `withRetry` reads that property by name. A `Retry-After` over 3000 ms is not waited for: the call fails at once and the next minute tick re-fetches. A header that is absent, unreadable or negative falls back to the 1 s / 2 s backoff.
    - Every GEXBot 429 calls `metrics.gexbotRateLimit(endpoint)`: a count of `gexbot.rate_limited`, attribute `endpoint` = the route with the ticker replaced (`/{ticker}/orderflow/orderflow`). Nothing is filed for a 429 a retry clears.

The run's status is unchanged: `deriveCronStatus` reports `partial` when some calls failed and `error` when all did, and the 10-event cap and summary message are unchanged.
    - The EOD report route is untouched. `requestEodReport` (`gexbot-eod.ts`) does not use `gexbotFetch` or `withRetry`, and it still maps a 429 to `{ kind: 'quota' }`, which stops `archive-gexbot-eod` for the day.
