# No test touches a real database

Status: approved by the owner 2026-11-04 (a standing rule, not a proposal). Phase A is in this change; phase B follows after 15:00 CT because it edits Railway service folders.

## Goal

No test, in any suite, may connect to or write to a real database. Each suite has one choke point where a connection attempt fails loudly, up front, instead of being noticed afterwards. In-process pglite stays allowed.

## Why

Several suites ran against whatever the shell exported. `.env.local` points at the production Neon database, and some ml tests read it or the repo-root `.env` file (`utils.load_env`, which overrides `os.environ`), so removing an env var never kept a run off a database. One ml test (`test_live_db_sum_invariant`) connected to whatever `DATABASE_URL` the shell had. `nightly/conftest.py` already forces a fake env and blocks non-loopback sockets; that is the model for the rest.

## The rule per suite

The block is the connect call itself, not the env: an env var can be set again by a loader, a file or a test.

## Env names stripped in every block

`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `POSTGRES_URL`, `POSTGRES_URL_NON_POOLING`, `POSTGRES_PRISMA_URL`, `NEON_DATABASE_URL`, plus the writable remote stores `KV_REST_API_URL`, `KV_REST_API_TOKEN`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`, `BLOB_READ_WRITE_TOKEN` and the `R2_*` credentials (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ENDPOINT_URL`, `R2_BUCKET_FULLTAPE`). A test that needs a value sets its own fake after the setup has run.

## Decisions

- `test_live_db_sum_invariant` was deleted, not skipped. Its check (stored lottery scores equal the component sum on 100 random rows) is kept as a manual, read-only script, `scripts/check_lottery_score_sum_invariant.py`, that says in its docstring that it reads production. Pytest does not collect it.
- A second Vitest layer that wraps `globalThis.fetch` to reject `*.neon.tech` was not added. Tests that stub fetch replace the wrapper, and every Neon client goes through the three mocked constructors anyway.
- Only database drivers are blocked in code. Redis, Blob and R2 are covered by stripping their env names; blocking their clients would be a separate change.

## E2E follow-ups found while verifying Part A (2026-11-04)

- **`e2e/entry-time.spec.ts` "changing time updates calculation results"** failed on main's CI at 2:01 PM CT. During market hours the entry time seeds from the CT wall clock (10:00 AM CT only outside them), the test selected 2 PM and expected the hours remaining to change, and the start was already 2 PM. It now pins the browser clock (`page.clock.setFixedTime`) in three cases (before the target hour, inside the 2 PM hour, outside market hours), each with a target that differs from the seeded start. No other spec depends on the seed: the rest set the entry time with `setEntryTime` or assert nothing about it.
- **`e2e/tracker.spec.ts` "opens add-contract modal"** was flaky on CI chromium and on WebKit, with or without the Part A route change (base and head flake at the same rate). `AddContractForm` autofocused Ticker on a 50 ms timer. Playwright's `fill()` is focus-then-insertText, so a timer that fired between the two steps of a later `fill()` moved focus back to Ticker: Ticker read "AMD200", the required Strike stayed empty and native validation blocked Save with no request sent. Two fixes: the spec waits for `toBeFocused()` on Ticker before the first fill, and the form skips the autofocus when focus is already inside the dialog (a fast typist could hit the same race). On WebKit with 6 workers, 24 repeats: 6 failures with neither fix, 0 with the spec wait alone, 0 Ticker-race failures with the form fix alone. No other `setTimeout(...focus())` exists in `src/`.
- **`reducedMotion: 'reduce'` was tried and not adopted.** The other WebKit-only failure on the tracker spec (a section toggle click landing mid-scroll under `html { scroll-behavior: smooth }` and `animate-fade-in-up`) was the reason. The setting belongs under `use.contextOptions` in Playwright 1.60 (a bare `use.reducedMotion` is not an option and is ignored). With it applied (checked from inside a page on all three browsers), chromium passes the whole suite (216 of 216 on the second run; the first run had three load flakes that pass in isolation). WebKit does not: five specs fail, three of them (`panel-reorder.spec.ts:89`, `toolbar-export-row.spec.ts:99` and `:117`) fail 12 of 12 with or without reduced motion, so they are pre-existing WebKit failures that no config change here affects. The tracker spec on WebKit, 30 repeats: 1 of 60 failed without it, 0 of 59 with it, too few to show a gain. The rule was to adopt only if the full suite passes on chromium and WebKit, so it is left out. WebKit runs only in the nightly all-browser job, not the CI gate. The tracker's own toggle miss is fixed inside `e2e/tracker.spec.ts` instead: its `beforeEach` calls `page.emulateMedia({ reducedMotion: 'reduce' })` before `goto`, which turns off the smooth scroll and the fade-in for that spec's pages only (the app already honours the media query), and the toggle is clicked once and checked for `aria-expanded`.

## Known gaps

- Python: constructing `psycopg2.extensions.connection(dsn)` directly bypasses `_connect`. Nothing in the repo does that.
- Vitest: a test file that mocks `@neondatabase/serverless` itself replaces the block, by design; its mock must not reach the network.
- The Python guards cover `psycopg2`, `asyncpg` and psycopg 3 (`psycopg`) by name. psycopg 3 is not a dependency anywhere, so its entries apply only in a venv that has it (a probe with a stand-in package proves them). Any other driver (`pg8000`) needs its connect point added to `_CONNECT_POINTS`. SQLAlchemy 2.1 resolves a bare `postgresql://` URL to psycopg 3, so `ml/src` builds its engines through `utils.make_engine`, which names `postgresql+psycopg2://`.
- uw-stream's socket guard wraps only `socket.connect` and `socket.connect_ex`. That covers the selector event loop (Linux CI, Railway). On Windows, asyncio uses the Proactor loop and `IocpProactor.connect` calls `ConnectEx`, which the guard does not see, so a path around the four asyncpg stubs is blocked on Linux and not on a Windows workstation. Loopback is allowed on both, so a bypass that reaches a Postgres on `localhost:5432` is not blocked either.
- sidecar: the psycopg2 mock blocks `connect` and `ThreadedConnectionPool` only. `SimpleConnectionPool` and the other children of the MagicMock still return MagicMocks (nothing in `sidecar/src` uses them). `sentry_sdk` is mocked only when no plugin imported it first.
- Vitest: the `afterAll` check does not run in a file whose tests are all skipped (Vitest runs no hooks for it), so a swallowed module-level attempt in such a file goes unseen.
- The scripts twin check (`scripts/test_guard_twins.py`) runs only where the scripts suite runs. CI does not run `scripts/test_*.py`.

## Acceptance

- Each block's self-test provokes an attempt (`psycopg2.connect("postgresql://x@invalid.invalid/db")`, `neon("postgres://…")`, `asyncpg.create_pool`) and sees it raise and be recorded; the test then discards its own entries (not the whole log, which would hide an earlier offender) so the session-end check stays green.
- Mutation check per block: disable the block, see its self-test fail, restore.
- Suite counts are unchanged apart from the deleted test and the new self-tests.
