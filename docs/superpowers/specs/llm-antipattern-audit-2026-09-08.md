# LLM Anti-Pattern Rules + Codebase Audit — 2026-09-08

## Goal

Turn a generic list of LLM-coding mistakes (unnecessary DI, hand-rolled crypto, unnecessary state, tracked-state leaks on failure, happy-path-only tests, load-everything I/O, complex locking, missed races, premature config) into repo-specific, checkable rules that the reviewer subagent applies on every diff, then audit the existing codebase once against those same rules and fix what has a concrete failure scenario.

## Why not just paste the list into CLAUDE.md

CLAUDE.md is already 285 lines. Generic prohibitions are not checkable and do not change behavior on a specific diff. The high-leverage placement is the `code-reviewer` agent checklist (fresh context, applied per change) plus a compact block in CLAUDE.md that points at the reviewer rules.

## The rules (R1–R7, v2 — revised after the 2026-09-08 audit)

**R1 — Module-level state must be bounded and dropped on failure.**
Vercel Fluid Compute reuses function instances, so anything at module scope in `api/` (`let`, `Map`, `Set`, array, cached promise) persists for the life of the warm instance. State that grows or caches needs a hard size cap or an eviction sweep on write; a TTL that is only checked on read is not a bound. An in-flight or pending marker must be dropped on rejection (`finally` or `.catch`); a promise deliberately cached as the value may persist after it resolves. State written on only one code path (so it cannot serve the fallback it exists for) is a finding. When the same artifact is cached on both sides of a service boundary (Vercel and Railway), refresh policies must match or a version handshake must exist. Exempt: warn-once booleans, lazy singletons, and maps keyed by a closed literal set. Long-lived Python processes (uw-stream, sidecar): dicts, queues, and sets keyed by ticker or contract need a cap or eviction, and a bounded drop policy must log or Sentry the first time it engages. React (`src/`): no derived or prop-mirrored values in `useState` (an editable draft seeded from a prop and guarded by a user-edited check is the auto-fill contract, not mirroring); every effect that subscribes, polls, or sets a timer returns a cleanup; network polling gates on `marketOpen` or an explicit session/time-window predicate.

**R2 — No hand-rolled crypto or secret handling.**
Secret comparison goes through `secretEquals()` / `bearerMatches()` in `auth-helpers.ts` (or `cronGuard` / `guest-auth`, which call them); never `===` or `.includes()` on a secret, and never a copy of the compare block. Randomness, and any hash used for integrity, identity, or authentication, come from `node:crypto`. A non-cryptographic hash used purely as a cache or storage-key discriminator is fine when a comment says so. Base64/base64url transcoding uses `Buffer`. Auth cookies are built by the shared cookie builders. A service split carries its auth gate with it: an endpoint moved between services keeps the same shared-secret check on both ends.

**R3 — Mock at the module boundary; no test-only indirection.**
Tests use `vi.mock` / `vi.mocked` / `vi.useFakeTimers` (Python: `monkeypatch`). No `deps` parameters, default-parameter injection (`fetchFn = fetch`, `nowFn = Date.now`), factories, single-implementation interfaces, or wrapper classes whose only consumer is a test. The tell is a comment saying "testable", "so tests can", "for fixtures", or "legacy callers": check for a double seam (a `vi.mock` of the same thing elsewhere, so the real path runs nowhere) or a `| None = None` / `?:` default that adds a production branch only tests exercise. Legitimate: decorators whose parameter is the wrapped thing, behavioural callbacks, sharing an already-constructed SDK client from the module that owns its config, threading a `sql` handle from one `getDb()` call (declare the handle type once as `Sql` in `db.ts`), and an integration executor that runs production SQL against pglite. `withDbReader` is the sanctioned wrapper.

**R4 — Failure-mode tests are part of "tests are mandatory".**
Every test file for a fetch wrapper, cron, endpoint, or DB writer covers: (a) upstream non-2xx / throw / timeout, (b) malformed or empty payload, including `res.json()` rejecting on a 2xx, (c) the DB write rejecting. Each asserts the failure is surfaced by name (`Sentry.captureException` / `logger.error({ err })` / 5xx / `status: 'error'`), not just `toBeNull()` or `toEqual([])`, and never relies on the mock response's default status. A cron whose DB write fails must not report `success`; per-leg write failures feed `deriveCronStatus`. A cron that returns `status: 'error'` must still produce a Sentry event. An empty upstream payload during market hours is surfaced (metric + `captureMessage`), not treated as a clean success.

**R5 — Stream or batch all I/O; count rows per run, not loop shape.**
A per-row awaited query is a finding when the loop bound is data-driven (rows, candles, alerts, fires) and exceeds ~50 per run; static enumerations of ≤20 items are exempt. DB writes are multi-row INSERTs (`unnest` / multi-VALUES) in ~500-row chunks; `sql.transaction(rows.map(...))` is one round trip and is fine up to ~1k rows. Objects whose size is unbounded by data growth, or over ~100 MB, are streamed or paged, never `readFileSync` + `Buffer.concat` + single `put()`. Pagination is bounded by rows AND bytes (Neon HTTP responses cap at 64 MiB; JSONB-heavy tables need a `pg_column_size` budget). A job that fetches a cumulative payload (session-to-date candles) diffs against a high-water mark before writing. DuckDB / polars predicate pushdown counts; a repeated glob scan per row does not. Long jobs log per-unit progress and are resumable.

**R6 — Prefer idempotent writes over locks; document any lease.**
Cross-instance and cron-overlap concurrency uses `INSERT … ON CONFLICT`, conditional `UPDATE … WHERE status = 'x' … RETURNING`, or a single lease row with expiry. The conflict key must derive from source data or a time bucket; a key that includes `NOW()` / `new Date()` never fires across runs. In-process locks and flags never provide cross-instance safety; use them only for genuinely per-process state and say so in a comment. A read-side memo cache is fine; a module flag that suppresses a write or a cron run is not. Any lease or lock comment states who renews it, what happens on renewal failure, how it expires, shows the TTL exceeds the holder's worst-case hold time including retries and HTTP timeouts, and declares fail-open or fail-closed at the acquire site; release is fenced (compare-and-delete). Read-modify-write on a shared row is one statement or a transaction. Client: any effect that ingests a fetched payload into accumulated or persisted state keys the ingest on a response-echoed identity (date, filter signature, request id), not on current props; every param-driven fetch aborts or supersedes its predecessor.

**R7 — No config until there are two callers.**
No env var, feature flag, or `constants.ts` entry for a single call site, unless it is an operational knob (rate cap, timeout, concurrency, queue size, kill switch) that must change without a deploy, and then the read site's comment says why. Domain constants that define one physical fact for the whole codebase (market hours, contract multipliers) live in `constants.ts` regardless of importer count. A new env var is read in code, declared in `api/_lib/env.ts`, and added to the CLAUDE.md env table and `.env.example` in the same commit; Railway-only vars are documented in the owning service's README. A retirement commit removes its config, scripts, and `.env.example` rows. Backstop: a vitest diffs `process.env.*` reads under `api/` against `envSchema.shape`.
