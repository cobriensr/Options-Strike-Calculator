# One review gate at a time (machine-wide lock)

**Status:** APPROVED by the owner on 2026-11-22 at 00:20 CT ("yeah"), with every default below as written: the hold cap at 75 min, a 3-min poll while queued, no fairness order, and the owner's terminal waiting like any other gate. Phase 1 (the lock library) is built, see "As built"; phases 2 to 5 are not.

**Review history:** three spec reviews, the most allowed.
- Draft 1 used the shell's PID, which dies between steps.
- Draft 2 used a lock file with a heartbeat, which left races.
- Draft 3 moved to an OS-held named pipe. Its review tried to break the pipe mechanism and couldn't, and found eleven detail problems. Draft 4 settles all of them, and they have not been re-reviewed.

## Goal

Make `npm run review` wait its turn, so that only one gate runs at a time across every worktree and session of this repo on the workstation.

Why: each gate runs about 15 vitest workers on the 16-core box. Two or three at once pin the CPU, slow the owner's machine, and fail gates on load timeouts in unrelated tests. On the night of 11-21 the CPU sat near 100% for hours, and one implementer's gate failed twice that way before passing.

## Background (checked against the code at HEAD 0ba2ba973)

- **The chain.** `package.json` `review` is one `&&` chain:
  - `node scripts/review-gate.mjs clear`;
  - `npm run type-check`, `eslint .`, `prettier --write …`, `vite build`, `check-build-output`, `vitest run --coverage` and `check-coverage-floor`;
  - `node scripts/review-gate.mjs seal`.
- **The seal guard.** `seal` refuses unless `npm_lifecycle_event` is `review` (`scripts/_lib/review-gate.mjs:80-81`).
- **How npm runs the chain.** `~/.npmrc` sets `script-shell` to Git Bash. npm 11.19.1 exports it as `npm_config_script_shell`, sets `npm_package_json`, and runs `bash -c <script>` (`@npmcli/promise-spawn`).
  - Each `&&` step gets its own short-lived parent process (probed 11-21). So nothing in today's chain lives for the whole run.
- **The common git dir.** `git rev-parse --git-common-dir` prints `.git` in the main checkout, `../.git` in its subfolders, and `F:/dev/strike-calculator/.git` in a linked worktree. Only the absolute form is the same everywhere.
- **The pre-commit hook.** `.githooks/pre-commit:8` runs `scripts/review-gate.mjs check`, in worktrees that may have no `node_modules` (`scripts/_lib/git-run.mjs:9`). `scripts/review-gate.mjs:95` runs `main` when it is imported.
- **The test fixtures.** `review-gate.cli.test.mjs` runs the CLI as a child process (`review-gate.fixtures.mjs:46-73`). `cleanEnv` drops `GIT_*`, `CLAUDECODE` and `NPM_LIFECYCLE_EVENT` (`:37`).
- **The review summary.** `review-summary.mjs` marks every stage before the one reached as `pass` (`:440`), and its zones only move forward.
- **CI.** CI runs `npm run review` (`ci.yml:210`) as a lone checkout.
- **The network block.** `src/__tests__/net-guard.ts:105-108` lets IPC pipe paths through.

**Pipe probes, 11-21, Node 24 on this box:**
- While a process listens on a pipe name, a second `listen` on the same name fails with `EADDRINUSE`.
- A client `connect` reads the holder's JSON.
- After the holder is hard-killed, a new `listen` succeeds at once.
- After the holder closes its server and destroys its sockets while waiters stay half-open, a new `listen` succeeds within 300 ms. A waiter's open end doesn't keep the name.
- Node 24's `net` supports Linux abstract sockets.

## Design

1. **A gate runner owns the chain.**
   - `review` becomes `node scripts/review-gate.mjs run`. The existing chain moves, unchanged, to a new `review:steps` script.
   - The runner reads `review:steps` from the file named by `npm_package_json` when it is set, else from `<cwd>/package.json`.
   - It runs the chain once with `spawn(cmd, { shell: process.env.npm_config_script_shell || true, stdio: 'inherit' })` and the environment it inherited. So `npm_lifecycle_event` stays `review` and `seal` keeps working.
   - It exits with the chain's code. A death by signal (`code === null`) maps to exit 1.
   - Running `npm run review:steps` directly can't seal, so it isn't a bypass.
   - **The runner logic** (spawn, hold cap, tree kill, exit-code mapping) lives in `scripts/_lib/gate-runner.mjs`, so it can be tested in-process. `scripts/review-gate.mjs run` only wires it up.
2. **The lock is a named pipe the OS holds.**
   - The name is `\\.\pipe\strike-calc-review-gate-<first 12 hex chars of sha1(key)>`, with the Linux abstract socket `\0strike-calc-review-gate-<same>` on Linux.
   - `key` is `realpathSync.native(path.resolve(cwd, rawCommonDir))`, lowercased on Windows. So the main checkout, its subfolders and every linked worktree get one name, whatever the drive-letter case.
   - Holding the lock means listening on that name. The OS frees it the moment the runner exits, however it exits.
3. **What the holder does.**
   - On each connection it writes one JSON line, `{ pid, worktree, startedAt }`, and keeps the socket open until it releases.
   - It attaches an `'error'` handler to the server and to every accepted socket, which logs and drops the error. A waiter that dies mid-handshake (EPIPE, ECONNRESET) can never crash the holder and free the lock under a running chain.
4. **The waiter's states.** One attempt runs at a time.
   1. *trying:* `listen`. On success it holds the lock: clear every wait timer and socket, then start the chain. On `EADDRINUSE`, go to *connecting*.
   2. *connecting:* `connect`, then read the holder's line.
      - A line that is missing, cut short or not JSON gives an unknown holder, and the waiter keeps waiting (R4).
      - Then go to *waiting*. `ECONNREFUSED` or `ENOENT` means the holder just left, so go back to *trying*.
   3. *waiting:* print `review-gate: waiting for the gate in <worktree> (pid <pid>, running <m> min)` straight away, then every 60 s.
      - When the holder's socket closes, go to *trying* at once.
      - A 15 s fallback timer also goes to *trying* if no close arrived. It never opens a second connection while one is open.
   4. Any other `listen` or `connect` error is a warning that names the pipe and the code. Retry at the next fallback tick. An error is never treated as "free".
5. **Wait cap.** After 120 min of waiting, exit 1. The message:
   - names the holder (worktree, pid, minutes running);
   - says the hold cap ends a hung holder at 75 min;
   - tells the reader to report to the owner and not stop another session's process. That rule is CLAUDE.md "CPU load".
6. **Hold cap (owner decision, default below).** If the chain is still running after 75 min, the runner kills the chain's process tree, releases the lock and exits 1, with a line saying which stage was running.
   - On Windows: `taskkill /T /F /PID <shell pid>`. Spawn without `detached`. Prove during the build that this reaches the vitest workers under Git Bash.
   - On Linux: spawn `detached: true` and kill the process group.
7. **Signals.** While holding, SIGINT and SIGTERM are passed to the chain: Windows Ctrl+C already reaches it, and on Linux the runner forwards to the group. The runner waits for the chain's `exit`, then releases. A waiter that gets a signal just exits.
   - **Known gap:** a hard kill of the runner frees the lock at once, while orphaned chain steps may keep running. Two gates can then overlap for the rest of that run. Accept it and note it in CLAUDE.md.
8. **Nothing else waits.** Single-file vitest runs, `npm run lint` and the Python `review:*` scripts don't take the lock. The CPU-load rules cover them.
9. **No bypass switch** (R7). The caps are module constants.
10. **Builtins only.** `gate-lock.mjs` and `gate-runner.mjs` import only `node:` builtins, because the pre-commit hook loads `review-gate.mjs` in worktrees with no `node_modules`.

## Thresholds

| Name | Value | Why |
|---|---|---|
| Progress line | at once, then every 60 s | A queued gate shows it's queued from its first second |
| Fallback retry | 15 s | In case a close event is missed; normally the close hands over at once |
| Handshake wait | 2 s | How long a holder gets to send its identifying line before the waiter shows it as unknown. A line that comes later still names it. Added in the Phase 1 build |
| Retry pause | 250 ms | After a refused connect, or a holder that hung up again, so a name that is taken but unreachable cannot spin the CPU. Added in the Phase 1 build; a released name was seen taking up to 300 ms to free on 11-21 |
| Refusals before the waiter speaks | 3 in a row | One or two refused connects are the blip a handover makes; the third prints one "unknown holder" line, so a name that answers nobody is not silent for the wait cap. Added in the Phase 1 build |
| Wait cap | 120 min | About four gates of queue, then fail loudly |
| Hold cap | 75 min | A passing gate takes about 18–28 min (1,105–1,676 s on record), so only a hung gate hits it. The owner may change it |
| Agent poll bound | about 200 min | Wait cap plus hold cap (195 min), so a queued agent never gives up on its own gate |

## Phases (at most 5 files each, tracked or local)

1. **The lock library:** `scripts/_lib/gate-lock.mjs`, `scripts/_lib/gate-lock.test.mjs`, and `vite.config.ts` (`SPAWN_TEST_FILES`: the test spawns a holder child).
   - API: `gatePipeName(rawCommonDir, cwd): string` and `acquireGateLock({ pipeName, holder: { worktree }, onWait }): Promise<{ release(): Promise<void> }>`.
   - Time comes from `Date` and timers only. Tests use `vi.useFakeTimers()`, a unique pipe name per test, and no injected parameters (R3).
2. **The runner library:** `scripts/_lib/gate-runner.mjs`, `scripts/_lib/gate-runner.test.mjs`, and `vite.config.ts` (`SPAWN_TEST_FILES`).
   - API: `runGate({ stepsCmd, shell, lock }): Promise<number>`, which spawns, enforces the hold cap, maps exit codes and releases in `finally`.
   - Tests run a real short child under fake timers, so 75 min can pass in a test without lowering the cap.
3. **The agent definitions** (local only, their own history). This lands before phase 4, so no agent gives up on a queued gate.
   - `implementer.md:70` and `verifier.md:37`: the poll bound becomes about 200 min. While the gate log's last line is a waiting line, poll every 3 min (owner default, below).
   - `db-migration-specialist.md:81` and `build-error-resolver.md:31,121`: the same note where they run `npm run review`.
   - `code-reviewer.md:36`: the chain text.
4. **Wire it in:**
   - `scripts/review-gate.mjs`: the `run` subcommand.
   - `package.json`: `review` and `review:steps`.
   - `scripts/_lib/review-gate.cli.test.mjs`.

   - `scripts/_lib/review-summary.mjs` and `review-summary.test.mjs`: waiting and wait-cap lines form a zone before type-check. A hold-cap line fails the stage it interrupted, so no stage after it reads as passed.

   - `CLAUDE.md`: "The Loop" chain text, "Commit gate" (waiting, both caps and the hard-kill gap), and a "CPU load" pointer.

## Tests (TDD)

**Phase 1, `gate-lock.test.mjs`:**
- `gatePipeName` gives the same name for a scratch main checkout, its subfolder and its linked worktree, and for an upper- or lowercase drive letter.
- **Free:** acquire. A client reads `{ pid, worktree, startedAt }`.
- **Held:** a second acquire calls `onWait` with the holder's details at once, then every 60 s.
- **Release:** a waiter wins on the holder's release with no 15 s wait.
- **Holder dies:** a spawned holder child is killed hard, and the waiter wins at once.
- **Three waiters:** exactly one wins per release, and the others keep waiting.
- **Waiter dies mid-handshake:** destroy a waiter right after connecting. The holder keeps the lock and serves the next waiter.
- **Malformed holder line** (missing, cut short or not JSON): the waiter prints an unknown-holder waiting line and keeps waiting.
- **No duplicate connections:** a fallback tick never opens a second connection, and a winner never connects to its own server.
- **Wait cap:** reject with a message naming the holder and its minutes running, saying "report to the owner".
- **R4:** a `listen` error other than `EADDRINUSE` (via `vi.spyOn(net.Server.prototype, 'listen')`) is reported by code and retried, never treated as free.

**Phase 2, `gate-runner.test.mjs`:**
- The chain's exit code passes through: 0 and non-zero.
- A signal death maps to 1.
- The lock is released on pass, fail and throw.
- **Hold cap:** under fake timers, a real sleeping child is tree-killed at 75 min. The runner exits 1 and releases, and the message names the stage.

**Phase 4, `review-gate.cli.test.mjs`** (scratch repos, each with a scratch `package.json` whose `review:steps` is a short `node -e` chain ending in `seal`):
- `run` executes `review:steps` and exits with its code.
- `seal` works inside `run`. `review:steps` run directly can't seal.
- With `npm_package_json` set explicitly to the scratch `package.json`, the runner reads it from there. Without it, the runner falls back to `<cwd>/package.json`.
- **Second run waits:** a second `run` started while a holder child holds the pipe prints the waiting line, then runs after the holder exits. It needs an async spawn, and the handover is event-driven, so the test costs no 15 s poll.

**Phase 5, `review-summary.test.mjs`:** waiting lines, a wait-cap exit, and a hold-cap kill during vitest. The last must fail at vitest, with coverage and seal not passed.

## Proof

- **Windows:** two worktrees start `npm run review` together. The second prints the waiting line and runs after the first ends. The CPU never carries two gates.
- **Linux:** CI passes, and the lock neither blocks CI nor breaks `seal`.

## Rollout

- Worktrees branched before this lands run the old `review`, with no lock, until they merge main.
- After the push, tell the peer sessions to merge main.

## Decisions (owner, 2026-11-22)

1. **Hold cap.** Yes, 75 min. A hung gate is killed by its own runner, so it never blocks every session.
2. **Poll cadence while queued.** 3 min while the gate log shows a waiting line, 30 s otherwise.
3. **Fairness.** No first-come order; the OS picks the winner at each release. Revisit if a gate loses twice in a row.
4. **The owner's terminal.** It waits like any other `npm run review`.

## As built: Phase 1 (2026-11-22)

`scripts/_lib/gate-lock.mjs` and its test follow Design 2 to 5, 9 and 10. What a later phase needs to know:

- **`onWait` gets one object**, `{ holder, runningMin, line }`. `holder` is `{ pid, worktree, startedAt }`, or `null` for a holder that did not identify itself. `line` is the text to print: `review-gate: waiting for the gate in <worktree> (pid <pid>, running <m> min)`, or `review-gate: waiting for the gate held by an unknown holder`. Phase 5's summary matches on the prefix `review-gate: waiting for the gate`. It prints at once for each new holder (a different gate took over) and every 60 s after.
- **The wait-cap rejection** is a plain `Error` whose message starts `review-gate: gave up after waiting 120 min for the gate`.
- **Three constants the spec did not list**, all exported for the tests and listed in the Thresholds table: `HANDSHAKE_MS`, `RETRY_MS` and `REFUSALS_BEFORE_ANNOUNCING`.
- **No retry loop runs without a pause.** A holder that hangs up before it speaks, one that names itself and hangs up again, and a refused connect are each retried after `RETRY_MS`. The first hang-up of a named holder is a real handover and is retried at once; the same holder hanging up a second time is something squatting on the name.
- **A waiter prints a waiting line only for a holder it has seen**, or for three refused connects in a row (one "unknown holder" line). A `listen` or `connect` error that is not one of the expected ones prints a warning only: a waiting line there would name a holder nobody has seen.
- **`HOLD_CAP_MS` (75 min) lives in `gate-lock.mjs`**, because the wait-cap message quotes it. Phase 2's runner imports it.
- **The caller's duty.** `acquireGateLock` fails closed: it resolves only after a successful `listen`, and the wait cap rejects. The caller must exit non-zero on a rejection and must never run the chain without the lock. There is no renew or TTL, because the OS ties the lock to the process. The 120 min wait cap is longer than one 75 min hold cap.
- **`gatePipeName` throws** (ENOENT) when the common git dir does not exist. The sha1 stays as specced, with a lint exemption (`sonarjs/hashing`): it only spells a pipe name.
- **Other platforms.** Windows gets the pipe form and Linux the abstract-socket form. `gatePipeName` throws on any other platform (macOS has no abstract sockets), so a gate there fails at once and says why.
- **Warnings** (a `listen` or `connect` error other than the expected ones, a failed waiter connection seen by the holder) go to stderr through `console.warn`, prefixed `review-gate:`.
