### 1. auto-prefill-premarket overwrites hand-saved data

- **Where:** `api/cron/auto-prefill-premarket.ts:156-165`. The UPDATE has no guard, and in EDT the schedule `30 13,14 * * 1-5` runs it again at 14:30 UTC (10:30 ET), after the owner may have saved by hand.
- **Discriminator check (done first):** the manual path is `POST /api/pre-market` (`api/pre-market.ts:90-96`), which builds its JSON from named fields only (`globexHigh`, `globexLow`, `globexClose`, `globexVwap`, `savedAt`). `preMarketBodySchema` (`api/_lib/validation/snapshot.ts:87`) is a plain `z.object`, which strips unknown keys, so a client cannot send `autoFilled` either. The UPDATE replaces the whole JSON, so a manual save also erases a prior `autoFilled: true`. The frontend reads `autoFilled === true` (`src/components/PreMarketInput.tsx:81`) to show the "Auto-filled" badge. So `autoFilled: true` is set only by the cron, and `pre_market_data->>'autoFilled' = 'true'` is a sound discriminator.
- **Fix:** the UPDATE becomes `... WHERE id = $id AND (pre_market_data IS NULL OR pre_market_data->>'autoFilled' = 'true') RETURNING id`; zero rows returned means a hand-saved row, and the run reports `skipped` with reason `manual_pre_market_data`. `->>` compared to the text `'true'` is used instead of the suggested `::boolean` cast so a malformed value can never throw.
- **One addition beyond the suggested guard:** `market_snapshots` can hold several rows for a date, and the cron picks "latest row". If the owner saved by hand on an older row and an analysis snapshot later created a newer row with a NULL `pre_market_data`, the guard alone would pass on the newer row, write auto data there, and `GET /api/pre-market` (latest row with a non-null `pre_market_data`) would then return the auto data and hide the hand-saved values. So the target row is chosen the way the reader chooses it: `ORDER BY (pre_market_data IS NOT NULL) DESC, created_at DESC LIMIT 1`.
- **Tests:** `auto-prefill-premarket.test.ts` (mocked SQL: the sequence is now bars, target row, UPDATE ... RETURNING; empty RETURNING gives `skipped`), plus a pglite test that runs the real statements against a `market_snapshots` table: manual row untouched, auto row refreshed, NULL row filled, missing row inserted, and the older-manual-plus-newer-empty case left alone.

### 13. wave2-confirmation: widen the lookback, alert on a lost slice (2026-11-04)

Hardening follow-up to item 12, from a review.

- **Gap.** After item 12 the cron labels a fire only at age 75 or more, and the candidate query stopped at `LOOKBACK_MIN` = 85. The ticks run every 5 minutes, so a fire was a candidate at only two of them (its first look, at most 5 minutes after it turns 75, and one retry). Two missed ticks in a row (a Vercel incident, or a Neon blip that outlasts `withDbRetry`) left about 5 minutes of fires NULL forever, silently; even one missed tick plus invocation jitter could drop a sliver. The old code had this slack only for fizzles. Now it applies to every label.
- **Lookback widened.** `LOOKBACK_MIN` = `SETTLE_AGE_MIN` + 15 = 90. A fire is now a candidate at three ticks, so two missed ticks in a row still leave one look. The partial index keeps the scan cheap; the `IS NULL` guard keeps it idempotent.
- **Post-close arithmetic is unchanged.** The gate is `isMarketHours(90)`, which runs to 17:30 ET. The last fire (about 16:05:59 ET) is first labelled at the 17:25 tick (age 79:01) and retried at 17:30 (84:01); both are inside 90. A 17:35 tick is gated off, though the fire would still be a candidate there (age 89:01), so the gate, not the lookback, ends the retries. At the very end of the day a fire still has only the one retry.
- **Lost-slice alert (last tick only).** On the cron's last tick of the session it counts, per table, the NULL rows triggered today (ET session) that are already older than `LOOKBACK_MIN`: the cron can never label them. One indexed `COUNT(*)` per table (a range over the partial wave2-pending index), skipped on every other tick.
  - **Last tick.** The ET minute equals the day's close plus `POST_CLOSE_EVAL_MIN` (90): 17:30 ET on a normal day, 14:30 ET on a half-day, taken from `getMarketCloseHourET` (the market calendar) and `getETTime`. It is the last minute `isMarketHours(90)` admits (the gate compares whole ET minutes with `<=`), so exactly one tick per session matches, and a holiday has none. If the 17:30 tick itself is missed there is no check and no alert (accepted).
  - **Alert.** If a table has any, one `Sentry.captureMessage` at level warning, fingerprint `['wave2-confirmation', 'lost-slice', <table>]`, tag `cron.anomaly: wave2-lost-slice`, and `extra` with the table, date, count, earliest and latest trigger time and the lookback. The message says `scripts/backfill-wave2-status.ts` repairs them (it labels any NULL row older than 2 h). A pino warning goes with it.
