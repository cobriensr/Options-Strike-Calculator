## Shared shape for every retrofitted script

- `--from/--to` (inclusive, ET trading days from `src/data/marketHours.ts`, holidays skipped), `--dry-run`, `--limit`, `--allow-market-hours`. A script that keeps a positional N splits argv first (`parseArgs` rejects unknown positionals).
- `--limit N` on a script that runs the day loop (`runDays`) is the first N trading days of the selected range, ascending. The caller slices the dates before calling `runDays`; `runDays` has no limit of its own. The two existing scripts keep their own meaning (range-pos: N ticker-days, newest first; net-prem: N ticker-days). The shared parser only checks that N is a whole number ≥ 1.
- Refuses 08:15–15:30 CT on weekdays unless `--allow-market-hours` (the existing `isMarketHoursCt` window in `range-pos-backfill.mjs`), checked before the run and again before each day, so a run started before 08:15 stops taking new days.
- UW requests through `fetchUwDayRows` (`scripts/_lib/uw-day-fetch.mjs`, already shared): one throttle at ≤300/min, an explicit per-script User-Agent, one retry after 1 s on a 429, 5xx, network error or timeout, and a 4xx read as an error, never an empty day.
- Per-day try/catch: a UW non-2xx, network error, malformed JSON or DB error is counted against that day and the run continues; the summary prints counts by day and by failure kind; exit 1 if any day failed (3 when the guard stopped the run and no day failed). No warn-and-exit-0 path.
- A day worker returns counts, not rows: `{ fetched, stored }` (whole numbers ≥ 0). `fetched` is the rows UW returned, before any filter; `fetched: 0` on a trading day shows up as an empty day in the summary, a hole to look at, not a failure. `stored` is the rows actually written, so 0 on `--dry-run`; a would-be count goes in an extra field such as `wouldStore`. Any extra fields are left unchecked and printed as `name value`; keep them small, since the summary holds them for every day of the run.
- `runDays` records one failure per day, the first. A worker that fans out over tickers, strikes or expiries uses `runDayItems(items, perItem, { concurrency = 1, label })`: it tries every item, sums the counts (extra numeric fields too), and if any item failed throws one `DayFailure` that keeps the first failure's kind (a `db`-tagged error stays `db`) with the message "k of n label failed; first (item): detail". The counts of the items that succeeded are lost then; the day is re-run, and its writes are idempotent. A plain `new Error` thrown at the end of a day is `other` whatever failed behind it (wrapping as `cause` keeps only `db` and `network`), and a bare `runPool` fan-out stops starting items after the first rejection, so neither is the pattern. `perItem` awaits the caller's throttle, so a concurrency above 1 shares it. `runDayItems` sums every numeric field across the items, so a ratio or any other non-additive extra goes on the totals the worker returns, not on the items.
- Each script validates at startup, before any day runs, that its item list (tickers, symbols) is non-empty and that its concurrency is a whole number ≥ 1, and exits `EXIT_BAD_ARGS` (2) if not. Otherwise an empty list reads as 33 empty days with exit 0, and a bad concurrency fails all 33 days as `other`.
- Writes in ≤500-row `unnest` (or multi-row VALUES) chunks with `ON CONFLICT` on the table's real unique key; no per-row `await` over >50 rows.
- Reuse, don't copy: the generic pieces live today in two script modules. From `scripts/_lib/range-pos-backfill.mjs`: `parseArgs`, `isMarketHoursCt`, `chunk`, `runPool`, `retryTransientDb`, `summarizeFailures`, `redact`. From `scripts/_lib/net-prem-ticks-backfill.mjs`: the `--from/--to` pairing rule in its `parseArgs`, `marketHoursRefusal`, `tradingDaysInRange`, `selectDates`, `createRequestThrottle`, `runTickerDays`, `summarizeByDay`. P3.0 moves them into one shared module, which both scripts then import.
- Tests: the shared module gets table tests; each script's row mapping and its correctness fix get a test in `scripts/_lib/*.test.mjs` (failure counting included, R4). Mock the DB and `fetch`; no test reaches a database.

## As built

### P3.0 Shared backfill CLI module

`scripts/_lib/backfill-cli.mjs` (test: `backfill-cli.test.mjs`). `range-pos-backfill.mjs` and `net-prem-ticks-backfill.mjs` import from it and re-export the moved names, so the two scripts and their old tests are unchanged.

What the retrofits import:

- Flags: `parseArgs` (from/to may come alone, the range-pos form) and `parseRangeArgs` (also requires both or neither and refuses `--to` after today in CT; net-prem's `parseArgs` is this one).
- Guard and dates: `isMarketHoursCt`, `marketHoursRefusal`, `tradingDaysInRange`, `selectDates`.
- Batching and UW pacing: `chunk`, `runPool`, `createRequestThrottle`, `UW_REQUESTS_PER_MINUTE` (300; moved with the throttle).
- Neon: `retryTransientDb`. It gained a tag in P3.0, so the move is not a pure move: it now labels whatever it throws (its 30 s deadline error too) as `db` for `classifyFailure`, by error identity. Two halves for a day worker: the closure passed to it holds the Neon call and nothing else, because anything thrown inside it is labelled `db`; and a Neon call outside it is not recognised as `db` (it lands in `other`), and a caught DB error must be re-thrown as it is, or wrapped with the original as `cause` (the label follows the error and up to five `cause` links, not a re-wrap without `cause`).
- Day loop: `runDays(dates, { allowMarketHours, secrets }, worker)` returns `{ days, stoppedBy, notRun }`, one day at a time, guard checked before each day (a run started before 08:15 stops taking new days at 08:15; the day in flight finishes). A rejected worker, or a worker that returns a `fetchUwDayRows` error outcome, becomes `{ date, ok: false, failure: { kind, detail } }`; the loop moves on. `secrets` is `{ uwKey, databaseUrl }` and the detail is redacted with it. The worker returns counts, `{ fetched, stored }` plus any extra fields (definitions under "Shared shape"); a return value without the two counts fails the day as `other`, and the message names the value's keys and the two counts, never its other values (`return await fetchUwDayRows(...)` reads "got keys kind, rows"). One failure is kept per day.
- Fan-out: `runDayItems` and `DayFailure` (see "Shared shape"). `classifyFailure` returns a `DayFailure`'s `kind` as given.
- Failure kinds (`classifyFailure`): `uw_http_<n>`, `network`, `timeout`, `malformed`, `db`, `other`.
- `summarizeRun(run)`: `attempted`, `succeeded`, `okDays` (each with its counts), `emptyDays` (done days with `fetched: 0`; they never change the exit code), `failedDays` (run order), `byKind` (most days first, ties by name, each with its dates and first example), `stoppedBy`, `notRun`, `exitCode`. `formatRunSummary(summary)` returns the printable lines: per-day counts and totals, failures by kind with dates and the first example, the empty days, the guard stop and the days not run. A failure detail or an extra field is printed on one line, its whitespace collapsed.
- Exit codes, exported as `EXIT_OK` 0, `EXIT_FAILED` 1, `EXIT_BAD_ARGS` 2, `EXIT_GUARD_STOP` 3.
- Older helpers kept as they were: `runTickerDays`, `summarizeByDay`, `summarizeFailures`, `redact`. The `--limit` error text is now generic ("a whole number"); neither existing script's own `--limit` docs changed.

Exit code of `summarizeRun`, by plain precedence: any failed day gives 1 (`EXIT_FAILED`), a guard stop included, so a failure is never reported as a plain stop; else a run the market-hours guard stopped gives 3 (`EXIT_GUARD_STOP`, the same code as the refusal before any work starts, as in `backfill-range-pos.mjs`), since the days in `notRun` are unfilled; else 0. `backfill-net-prem-ticks.mjs` does not use the day loop: it puts its guard stop ahead of failures (3 even when ticker-days failed), keeps that order and its abort on a non-transient DB error, and is left unchanged.

### P3.1 Candles

Files: `scripts/_lib/candles-backfill.mjs` (+ test), `scripts/_lib/schwab-local.mjs` (+ test), `scripts/backfill-etf-candles-1m.mjs`, `scripts/backfill-spx-candles-1m.mjs`. `scripts/backfill-ndx-candles-1m.mjs` is deleted. `scripts/backfill-market-internals.mjs` now imports its token code from `schwab-local.mjs`.

- **One script for SPX and NDX.** `backfill-spx-candles-1m.mjs` fills both symbols per day, like the live cron (the file keeps its old SPX name, as the cron does). To fill one symbol you re-run both: the writes are DO NOTHING. Run `backfill-etf-candles-1m.mjs` first (the dark-pool reader divides an index bar by the matching ETF bar).
- **Flags.** `--from` and `--to` are required (no lookback default, no positional N), inclusive trading days; `--to` must be before today in ET (the live crons own today, and its last bar is still forming); `--dry-run`, `--limit N` (first N trading days), `--allow-market-hours`. A day worker is `processEtfDay` / `processIndexDay` over `runDayItems` (tickers SPY, QQQ; symbols SPX, NDX), returning `{ fetched, stored, kept, dropped, emptyItems }`: `kept` is the rows that passed the live cron's filters (the would-be count on a dry run), `dropped` the bars left out (malformed, another ET day, a repeated minute), so `kept + dropped = fetched`, and `emptyItems` how many of the day's tickers or symbols UW sent no bars for. `emptyItems` exists because the other totals hide a hole: SPY empty and QQQ at 960 bars reads `fetched 960 stored 960`, and SPY and SPX have no rows for the day. It shows in the day's line and again in the end-of-run summary as "partly empty days (...): <date> (1 empty)" (`summarizeCandleRun`, which wraps the shared summary). Like a wholly empty day, which the shared summary already lists as an empty day, it is a hole to look at, not a failure: the exit code is unchanged. SPX is SPY's bars scaled, so an empty SPY leaves SPX empty too. The item lists are constants and the concurrency is 1, so there is no startup list check to fail.
- **Ratio source.** Neon holds only SPX's Schwab daily close (`outcomes.settlement`), so all four closes come from Schwab `/pricehistory`, daily candles (`periodType=year&frequencyType=daily&frequency=1&startDate&endDate`), one call per symbol (`$SPX`, `SPY`, `$NDX`, `QQQ`) over the range padded by two days. A candle's stamp is read as an ET date, as `fetch-outcomes.ts` does; a stamp that lands on a non-trading day fails the fetch as `malformed` (the mapping would shift every ratio). Ratio of a date = index close ÷ ETF close for that date. Before any day runs the script prints the table of closes and ratios. Run that first: SPX's close should equal `outcomes.settlement` for the date.
- **No ratio is a failed day, by name.** A date with no close, a Schwab HTTP error or a token that can't be had fails that symbol's day (`runDayItems`: the day fails with the first failure's kind) before UW is asked for that symbol, and nothing is written for it. The kind is the Schwab failure's own where it has one (`network`, `timeout`, `malformed`) and `other` otherwise, with the detail "no ratio for SPX on <date>: Schwab has no $SPX daily close for <date>". No fallback ratio exists in the code.
- **Sample ratios (test fixture, made-up closes; the real ones print at the start of a run).** SPX 6401.28 ÷ SPY 637.14 = 10.0469; SPX 6455.92 ÷ SPY 642.55 = 10.0473 (the next day); NDX 23510.5 ÷ QQQ 573.2 = 41.0162.
- **`spx_schwab_price` / `ndx_schwab_price`: NULL on every backfilled row.** Readers: `getSpxCandles` (`api/_lib/db-claude-tools.ts`, maps NULL to null) and the `get_spx_candles` tool text ("when present", `api/_lib/claude-tools.ts`); the 2026-05-21 periscope-rules study query and `_probe-dealer-tri-overlap.ts` (one-off research scripts); nothing in `src/` or `ml/`, and `dark-pool-query.ts` reads only `close`. On a live row the column holds the Schwab index price read seconds after that minute closed, and "use it for precise price level claims". No per-minute Schwab price exists for these days, and the day's close is already in `outcomes`. The daily close on every row would claim a per-minute check that never happened; on the last bar only it would be one true value among 389 NULLs that no reader needs.
- **What a row is.** As the live cron: all sessions UW returns (`pr`, `r`, `po`), prices times the ratio, volume a whole number, `market_time` checked, `date` the ET day, ON CONFLICT DO NOTHING on `(symbol, date, timestamp)` (etf: `(ticker, timestamp)`), ≤500 rows per INSERT. Differences from the old scripts: `limit=2500` (UW's cap; the etf script sent none and read a 500-bar slice) with a day that reaches 2500 bars failing as cut short, and a bar on another ET day dropped (the dark-pool join is on the timestamp alone). Differences from the live cron, on purpose: no high-water mark and no forming-bar filter (every bar of a finished day is closed), and a bar UW sends without a string `start_time` makes the answer `malformed` (the day fails) where the cron drops that bar.

- **Token lift.** `schwab-local.mjs` holds the Upstash read, the refresh and its compare-and-set (the Lua is unchanged), `redactBody` and the env read, as functions that throw `SchwabAuthError` instead of `process.exit(1)`. `backfill-market-internals.mjs` catches it and exits 1 as before. ### P3.2 `flow_data`, part 1

A script is a spec (`MARKET_TIDE`, `ETF_TIDE`, `NET_FLOW`): its items, URL, User-Agent, UW row field and `toRows`.

- **Lifted into `backfill-cli.mjs` first, as its own commit.** `planRangeDays(argv, why)` (the P3.1 flag plan), `storeRows` + `WRITE_BATCH` (the ≤500-row INSERT ... ON CONFLICT DO NOTHING) and `summarizeItemRun(run, n, label, noun)` (the "partly empty days" line) were in `candles-backfill.mjs`; a second copy of each would have been the copying the plan rules out. `candles-backfill.mjs` delegates (`planCandleDays`, `summarizeCandleRun`) with the same messages and output; its tests only changed their import names (`storeCandleRows` → `storeRows`, `WRITE_BATCH` from `backfill-cli.mjs`).
- **Callers checked, positional N dropped.** A grep of the repo (Makefile, package.json, `.github`, `scripts/README.md`, docs) found no caller of the three scripts; the only mentions are prose lists. So, like the candle scripts, there is no lookback default, no positional N and no ticker list: `--from/--to` are required, `--to` must be before today in ET. Why that is safer than N: `getTradingDays(N)` counts weekdays back from today, holidays and the unfinished day included, and the ETF tide endpoint answers `?date=<today>` with zeros (per `fetch-etf-tide.ts`), which an N run would have stored for today and DO NOTHING would have kept. To fill one source, run all of them (the writes are DO NOTHING; one extra UW request per skipped source and day).
- **The key.** `flow_data` is `UNIQUE (date, timestamp, source)` (migration #4, `api/_lib/db-migrations.ts`); no later migration changes it. A test reads the migration and fails if the CREATE TABLE's key or columns differ from `FLOW_DATA_TARGET`. DO NOTHING, so 07-22 keeps its live morning rows (market tide 17 of 80, net flow 16, per the inventory). 09-04 has a full net-flow series from a catch-up run (90/82/81 rows), which this fills only where it has holes, and one market-tide row, which it fills.
- **What a row is.** `date` is the ET day asked for, and a UW row whose timestamp falls on another ET day is left out and counted (`dropped`); the old market-tide and net-flow scripts stored it under the row's own `date`. Market tide: the 5-minute rows with UW's timestamp unchanged (the live cron stores them as sent), premiums as numbers. ETF tide: one row a minute from UW, the last row of each 5-minute window kept, stamped at the window start. Net flow: the minute ticks added up, the running total kept at the last tick of each window. Differences from the live crons and the old scripts, on purpose: (1) ETF-tide rows and net-flow ticks are put in time order before "last of a window" and before the running sums (the cron relies on UW's order; the old netflow script already sorted, the old etf script did not); (2) in the two tides a row whose premium is not a number is left out and counted, where the old etf script and the live ETF cron store a 0 (the cron also counts a metric); in net flow a tick with a bad premium stays in the running sums with that premium as 0 and its own volumes, as the live cron's `|| 0` does, and is counted in `dropped`, because leaving the whole tick out would shift every later row's `net_volume` by its volumes (the code review's probe saw 4426 live against -587 backfilled); (3) an absent `net_volume` is stored as NULL, where the old etf script and the live ETF cron (`api/cron/fetch-etf-tide.ts:84`, `row.net_volume || 0`) store 0; NULL is kept on purpose, since the readers print it as N/A (`db-flow.ts:104`, `db-claude-tools.ts:189`); (4) in the two tides a `net_volume` outside the INTEGER range, or a premium outside DECIMAL(14,2), is left out and counted, instead of failing the whole INSERT (UW sends tide values already added up, so a bad value spoils only its own row); (5) net flow is different, because this script adds the ticks up itself: one corrupt tick moves every later total, and dropping rows one by one would quietly strip the rest of the day. If a running ncp, npp or net_volume leaves its column's range, the item fails as `malformed`, naming the source, the date, the column and the first minute, and nothing is stored for it (before, Postgres rejected the INSERT and the item failed as `db`).
- **Worker counts.** `{ fetched, stored, kept, dropped, emptyItems }`. `kept` is the flow_data rows the mapping made (the would-be count on `--dry-run`, where `stored` is 0); `dropped` is the UW rows left out as unusable (for net flow it also counts the ticks whose premium counted as 0, which are still in the sums). Market tide: `kept + dropped = fetched`; for the two sampled sources the rows that are not dropped collapse into the 5-minute rows, so `kept` is lower. `emptyItems` is how many of the day's sources UW sent no rows for; the summary lists those days as "partly empty days (UW had no rows for some of the N sources ...)", like the candles: a hole to look at, exit code unchanged.
- **Failures counted by name.** UW non-2xx (`uw_http_<n>`, a 4xx never an empty day), network, timeout, a body that is not JSON, a row without its timestamp field, or an item the two guards below reject (`malformed`), and a database error (`db`). The audit's "DB insert errors are only warned about" is gone: a rejected write fails the day, names the source, and the run exits 1. `fetchUwDayRows` at ≤300/min with one retry after 1 s. User-Agents: `strike-calculator-market-tide-backfill (node)`, `strike-calculator-etf-tide-backfill (node)`, `strike-calculator-netflow-backfill (node)`. The item lists are constants and the concurrency is 1, so there is no startup list check to fail. A failed source's day writes nothing for it but the other sources still run and write.
- **Two guards, one per way a bad UW answer would pass as a healthy day.** After the mapping an item fails the day as `malformed` (a `DayFailure`, so the kind is kept) and writes nothing when (a) UW sent rows and none is usable for the day, as when UW ignores `?date=` and answers another ET day (without the guard: `kept 0, dropped N`, exit 0), or (b) it has ten or more rows and every premium is zero. Ten is the floor of the live cron's `checkDataQuality` (`minRows` 10, which alerts above it; this fires at 10). Without them DO NOTHING would keep the outcome for good, and a per-day row count would not show zero-valued rows. Each guard has a test in every script's block, and so does the case that must pass (nine zero rows, or one real premium among many). A guard can't see a partly wrong answer: a day with some usable rows and some wrong ones is stored as it is. Nothing here repairs a wrong row already stored (a live row for the same key stays).
- **Commands (controller; after 15:30 CT or at a weekend).** One-day dry-run probe per script, on Thursday 2026-07-23, the first day with no live rows. Each reads UW (2, 2 and 3 requests), builds no Neon client and writes nothing: `node --env-file=.env.local scripts/backfill-local.mjs --from 2026-07-23 --to 2026-07-23 --dry-run`, `node --env-file=.env.local scripts/backfill-etf-tide.mjs --from 2026-07-23 --to 2026-07-23 --dry-run`, `node --env-file=.env.local scripts/backfill-netflow.mjs --from 2026-07-23 --to 2026-07-23 --dry-run`. A dry run prints counts, not values: `kept` and `dropped` show a day whose rows are on another ET day, and the two guards fail a day with no usable or all-zero rows by name. Read `kept` against the live days: about 80 per market-tide source, 78 per ETF-tide ticker (156 for the two on 07-22), and 80–90 per net-flow ticker (09-04's catch-up wrote 90/82/81). The same without `--dry-run` is the one-day write; the full range is `--from 2026-07-22 --to 2026-09-04` (66, 66 and 99 UW requests).
