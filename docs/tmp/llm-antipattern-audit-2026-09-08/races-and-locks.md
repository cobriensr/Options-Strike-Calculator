# races-and-locks audit — 2026-09-08

Rule under test: **R6** — prefer idempotent writes over locks; any lock/lease must document who renews it, what happens when renewal fails, and how it expires; cross-instance concurrency is handled with `INSERT … ON CONFLICT`, single-statement conditional `UPDATE … WHERE … RETURNING`, or a single TTL'd lease — never in-process mutexes/flags/sleeps; read-modify-write on shared rows must be one statement or a transaction.

Scope covered: `vercel.json` crons (89 schedule entries → 77 handlers; the 39 with interval ≤ 10 min read end-to-end), `api/_lib/schwab.ts`, `api/_lib/db.ts` + `db-migrations.ts` (runner + the 13 legacy `run:` migrations), `api/journal/**`, `api/analyze.ts`, every Redis writer in `api/` (12 sites), the four per-instance in-memory caches, `uw-stream/src/**` (lease, connector, router/handler lifecycle, all 6 handler sinks + `db.py`), `sidecar/src/**` (seed endpoint, ingestion loop, writers), every `src/hooks/*.ts` that performs its own fetch (34 hooks) and the 10 components with inline fetch-in-effect. ## Findings

### RL-01: Never-vanish union ingests the PREVIOUS filter's still-held response into the NEW filter's slot on the same commit  [P1] [confidence: high] [effort: M]

- Where: `src/hooks/useStickyUnion.ts:357-392` (reset-on-storageKey effect) and `:407-474` (ingest effect, deps `[items, storageKey, tombstones]`); `src/hooks/useFetchedData.ts:136-168` (`fetchOnce` keeps `prev.data` while the new URL is in flight); `src/hooks/useLotteryFinder.ts:219-260` (ownership guard compares only `offset`); `src/components/LotteryFinder/index.tsx:697-757`, `src/components/SilentBoom/index.tsx:765-812`.
- What: `useFetchedData` is stale-while-revalidate: when `url` changes it sets `loading:true` but leaves `state.data` (the previous URL's response) in place until the new response resolves. The feed components build `storageKey = feed-union:<feed>:<date>:<filterSig>` from the SERVER-side filters and pass `fetched: engaged ? rows : []` into `useNeverVanishFeed → useStickyUnion`. On the render where a server filter changes, `storageKey` changes AND `items` is still the old filter's rows. `useStickyUnion` runs its effects in declaration order on that commit: the reset effect swaps in the new (empty/rehydrated) slot, then the ingest effect upserts every old-filter row into the new slot and schedules the localStorage persist. The `retain` predicate checks only same-day + premium floor (`LotteryFinder/index.tsx:722-727`, `SilentBoom/index.tsx:790-794`), so rows excluded by takeit floor, conviction/minScore, fire-count floor/cap, mode, optionType, tod, reload, cheapCallPm, showAll, or ticker are pinned in the new slot and — by the never-vanish contract — never leave it for the day. `useLotteryFinder`'s page cache has the same blind spot: `:219-235` stores the old-filter payload under the new URL because the ownership check is `offset`-only.
- Interleaving: t0 the trader raises the TAKE-IT floor 0.70→0.85 (or clicks a ticker chip) → React commits: `filterSig` changes, `lotteryFinder.data` is still the 0.70 response (SWR) → `useStickyUnion` reset effect loads slot `…:sig085` (empty), ingest effect upserts the 0.70 rows into `…:sig085` and persists them. t1 the 0.85 response lands with the qualifying subset → those upsert; the non-qualifying 0.70 rows remain pinned-but-absent → rendered under the 0.85 filter for the rest of the day, and rehydrated from localStorage on reload. Deterministic (effect ordering), not timing-dependent. The regression test that claims to cover this (`LotteryFinderSection.test.tsx:833-859`) mocks `useLotteryFinder` to return the post-filter response synchronously in the same render as the click — exactly the SWR window the real primitive does not provide — so it passes while the production path carries over.
- Fix: gate ingest on a response-echo match. Both responses echo `filters` (`LotteryFinder/types.ts:412-423`, `SilentBoom/types.ts:213-225`): extend `useFetchedData`'s `requestKey`/`responseKey` to `${date}|${filterSig}` (build the same sig from `d.filters`; make sure every sig field is echoed — SilentBoom's `minDte/minPremium/hideLatePm/minTakeitProb/ticker` are not all in the visible echo) so `gatedData` is `null` while the new-sig request is in flight; or in the component, `fetched: sigFromResponse(data) === filterSig ? rows : []`. Then fix the test to return the OLD response first and the new one after an `await`.

### RL-02: `usePinSetupStatus` — date change vs in-flight live poll, no cancellation → stale overwrite  [P1] [confidence: high] [effort: S]

- Where: `src/hooks/usePinSetupStatus.ts:84-125` (used by `PinSetupTile/index.tsx:61`).
- What: `doFetch(currentDate)` is a bare `fetch(url)` with no `AbortController`, no timeout, no request-id; the only guard is `mountedRef`. The mount/date effect calls `doFetch(date)` and `usePolling` calls `doFetch(null)` (live) every `POLL_INTERVALS.PIN_SETUP` while `date == null`. Whichever response resolves last wins `setData`.
- Interleaving: t0 poll tick issues `doFetch(null)` and Neon is slow; t0+200 ms the trader picks date D → `doFetch(D)`; t0+500 ms D returns → `setData(D)`; t0+1.5 s the live response lands → `setData(live)` → the tile shows today's live status under the selected historical date, and since polling stops while `date != null` nothing corrects it until the next date change. Reverse order (D1 slow, D2 fast) shows D1's data labeled D2.
- Fix: `abortRef.current?.abort(); const ctrl = new AbortController(); abortRef.current = ctrl;` per `doFetch`, pass `signal: ctrl.signal`, `if (ctrl.signal.aborted) return` before every `setState` (the pattern in `useTrackerContracts.ts:99-121`); or migrate to `useFetchedData` with `url` derived from `date`.

### RL-08: Schwab refresh lock — `releaseLock` is an unfenced `DEL`, and `LOCK_TTL` equals the Schwab fetch timeout with no headroom  [P2] [confidence: high] [effort: S]

- Where: `api/_lib/schwab.ts:143-169` (`LOCK_TTL = 30`, `releaseLock → redis.del(LOCK_KEY)`), `:201` (`AbortSignal.timeout(30_000)`), `:94-113` (`storeTokens` retries with 500 ms + 1000 ms sleeps), `:269-283` (`finally { await releaseLock() }`).
- What: The lock is `SET NX EX 30` with constant value `'1'`; release deletes the key unconditionally. The holder's critical section is `refreshAccessToken` (≤ 30 s) + `storeTokens` (≤ ~1.6 s of retries), so the lock can expire while the holder is still inside it, and the holder's `finally` then deletes whichever instance acquired next. The comment "must be >= SCHWAB_API timeout" documents the intent; the arithmetic is `==`, not `>=` plus store time.
- Interleaving: t0 instance A acquires; Schwab stalls; t0+30 s the key expires and A's fetch aborts; t0+30.05 s instance B (a waiter polling every 300 ms) acquires and refreshes with the pre-lock token R1; t0+30.1 s A's `finally` runs `DEL` → B's lock is gone; t0+30.3 s waiter C reads no lock, reads stale tokens, loops to `acquireLock` → succeeds → B and C both call Schwab with R1 concurrently. With rotation the second call fails (`token_error` for that request); if Schwab honours a reuse grace the two chains' `storeTokens` are last-writer-wins and Redis can end holding the chain Schwab invalidated → next refresh fails → forced re-login.
- Fix: fence the lock with a per-attempt token (`randomUUID()`), release via the same Lua CAS-DEL uw-stream already uses (`ws_lease.py:82-86`), and set `LOCK_TTL` ≥ fetch timeout + store retry budget (e.g. 45 s).

### RL-09: Schwab refresh winner never re-reads Redis after acquiring the lock; it refreshes with the token it read BEFORE the lock  [P2] [confidence: medium] [effort: S]

- Where: `api/_lib/schwab.ts:332-374` (`getStoredTokens` → expiry check → `refreshAccessTokenOnce(stored.refreshToken, …)`), `:262-284` (winner path uses the passed-in `refreshToken`).
- What: The waiter path re-reads after `waitForLockRelease`; the winner path does not. If another instance completed a full refresh between this instance's `getStoredTokens` and its successful `acquireLock`, the winner calls Schwab with the already-rotated refresh token. Medium confidence only because the outcome depends on Schwab's rotation/grace semantics, taken from the brief rather than probed.
- Interleaving: t0 instances A and B both read `{R1, expired}`; t0+5 ms A acquires, refreshes R1→R2, stores, releases at t0+700 ms; B's first `SET NX` was delayed by an Upstash latency spike and succeeds at t0+750 ms → B calls Schwab with R1. Rotation-strict: rejected → B throws → `getAccessToken` returns `token_error` → that request/cron fails although Redis holds a valid R2. Grace semantics: B gets R3 (invalidating R2) and stores it — fine unless A's `storeTokens` was mid-retry and lands last (RL-08).
- Fix: double-checked read inside the lock — after `acquireLock`, `const latest = await getStoredTokens(); if (latest && Date.now() < latest.expiresAt - BUFFER_MS) return latest;` and refresh with `latest.refreshToken`, not the argument.

### RL-11: Schwab `acquireLock` fails OPEN after three Redis errors — the comment says a lock holder is the only caller of Schwab, but this path makes every instance a "holder"  [P3] [confidence: high] [effort: S]

### RL-12: uw-stream lease fencing deadline ignores the per-attempt HTTP timeout → ~15 s double-holder window under asymmetric Upstash unreachability  [P3] [confidence: high] [effort: S]

- Where: `uw-stream/src/ws_lease.py:369-397` (`max_consecutive_faults = ttl_ms // renew_ms` = 3; loop is `sleep(renew_s)` then `renew()`); `main.py:41` (`_LEASE_HTTP_TIMEOUT_S = 5.0`); `config.py:198-199` (TTL 30 000 ms, renew 10 000 ms).
- What: The docstring says three consecutive faults "span the full TTL". With a 5 s HTTP timeout per failed attempt the cadence is 15 s, so the third fault is confirmed ~45 s after the last successful PEXPIRE while the key lapsed at 30 s. If Upstash is unreachable from the old container but reachable from a booting one, the new generation acquires at ~30–32 s and opens its 8 sockets while the old generation still holds its 8 for up to ~15 s — the 16-connection overlap the lease exists to prevent. Needs an asymmetric partition, so P3; renewal/failure/expiry semantics are otherwise fully documented.
- Fix: fence on wall-clock — record `last_ok = loop.time()` on each successful `renew()` and fence when `loop.time() - last_ok >= ttl_ms/1000` regardless of attempt count; or `max_consecutive_faults = ttl_ms // (renew_ms + http_timeout_ms)`.

### RL-13: `refresh-tracker-contracts` auto-expire UPDATE has no `AND status = 'active'` guard → can overwrite a concurrent manual close; tick inserts have no key  [P3] [confidence: high] [effort: S]

- Where: `api/cron/refresh-tracker-contracts.ts:304-332` (`UPDATE tracker_contracts SET status='expired', closed_at=NOW(), closed_price=COALESCE(…) WHERE id = ${c.id}` — no status predicate; selected via `SELECT … WHERE status='active'` at `:670-679` and `c.expiryDate < todayIso`), manual close `api/tracker/contracts/[id].ts:113-149` (`UPDATE … WHERE id = ${id}`, also unguarded); `tracker_contract_ticks` insert `:361-380` with `fetched_at = new Date()` and no UNIQUE (`db-migrations.ts:4650-4663`).

### RL-14: `monitor-vega-spike` confluence flag is derived from in-process "which inserts were mine", so two overlapping runs that each own one ticker's insert never write `confluence = true`  [P3] [confidence: high] [effort: S]

- Where: `api/cron/monitor-vega-spike.ts:229-272` (sequential SPY then QQQ `evaluateTicker`, `newSpikes[ticker]` only when `outcome.fired && newRowId != null`, then `if (spySpikeInfo && qqqSpikeInfo)` → `UPDATE vega_spike_events SET confluence = true WHERE (ticker, timestamp) IN (…)`); inserts are `ON CONFLICT (ticker, timestamp) DO NOTHING RETURNING id` (`:163-174`, index `db-migrations.ts:2557`).

### RL-15: Append-only or wall-clock-keyed cron writers whose `ON CONFLICT` target cannot dedupe across runs (`gexbot_snapshots`, `gexbot_api_capture`, `greek_exposure`, `zero_gamma_levels`, `futures_snapshots`)  [P3] [confidence: high] [effort: S]

### RL-16: `migrateDb()` has no cross-caller serialization; safe today only because its callers are manual owner endpoints  [P3] [confidence: high] [effort: S]

- Where: `api/_lib/db.ts:398-440`; callers `api/journal/init.ts:31`, `api/journal/migrate.ts:27` (owner-gated; no cold-start auto-migrate — verified by grep); legacy non-atomic path `:436-441` (`run` then a separate `INSERT INTO schema_migrations`); migration #6 (`db-migrations.ts:187-188`) is `ALTER TABLE … ADD CONSTRAINT` without `IF NOT EXISTS`.

- Fix: `SELECT pg_advisory_xact_lock(…)` inside a transaction per migration, or state in the `migrateDb` docstring that concurrent callers are not serialized and the PK is the guard.

### RL-17: `writeLastGood` is an unconditional overwrite — a slow, older request can replace a newer last-good snapshot  [P3] [confidence: high] [effort: S]

## Rule tweaks — how to reword R6 if it would misfire on legitimate code here

1. **Exempt process-local memory guards.** R6 says "never with in-process mutexes" — `recent_fires._lock`, `archive_seeder._seed_lock`, `batched_writer`'s buffer lock and `archive_query`'s `BoundedSemaphore` guard in-memory state or a single-process resource (a volume seed, DuckDB handles) and are correct. Reword: "in-process mutexes/flags never provide cross-instance safety; use them only for state that is genuinely per-process and say so in a comment."
2. **Read-side memoization is not a lock.** Add: "a module-level cache that only avoids repeated READS is fine; a module-level flag that suppresses a WRITE or a cron run is the anti-pattern."
3. **`ON CONFLICT` only counts when the key is the logical bucket.** Six writers in this repo have a conflict target that includes `NOW()`/`new Date()` (RL-05, RL-07, RL-15) and one whose key is a tick rather than the cooldown bucket (RL-06). Add: "the conflict key must be derivable from the SOURCE data or a time bucket — a wall-clock timestamp in the key means the clause never fires across runs."
4. **Client-side: SWR carryover is a race too.** R6 is server-worded. The P1s here are (a) missing per-request cancellation and (b) a stale-while-revalidate payload ingested under a new key. Add a client clause: "any effect that ingests a fetched payload into accumulated/persisted state must key the ingest on a response-echoed identity (date, filter signature, request id), not on the current props; every param-driven fetch aborts its predecessor."
5. **Lease docs should include the arithmetic.** Both Redis locks state a TTL; only uw-stream derives it from the renew interval, and neither derives it from the critical section's worst-case duration including retries and HTTP timeouts (RL-08, RL-12). Add: "state the TTL and show it exceeds the holder's worst-case hold time."
6. **Fail-open must be declared at the lock.** `uw-concurrency.ts` documents its fail-open in the header; `schwab.ts` hides it inside `acquireLock`. Require the failure-mode sentence at the acquire site, not only in the module header.
